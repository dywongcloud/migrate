# daedal -- working notes for agents

Non-obvious constraints for the VM/kernel path. Read before touching it.

## Host / VMs
- macOS Apple Silicon. Two dedicated Lima VMs: `daedal-kvm` (vz, aarch64, `nestedVirtualization:true` -> real `/dev/kvm`) and `daedal-pvm` (qemu/TCG, x86_64, for the PVM kernel). The user's `hive` VM is off-limits.
- The build/demo/bench scripts in `scripts/` run *inside* a Lima VM: they use Linux-only tooling (`mkfs.ext4`, `mount -o loop`, `ip`, `podman`, `make`, `/dev/kvm`). Lima mounts `/Users` into the VM at the same path, so the hardcoded `/Users/dylanwong/daedal` paths resolve identically there. Each such script sources `scripts/lib/guard.sh` and calls `require_linux` up front; run on the macOS host, the guard transparently re-executes the script inside the running VM (`limactl shell`, arguments and exit code preserved), so the same command works from either side. `DAEDAL_VM` overrides the target (default `daedal-kvm`; `daedal-pvm` for the PVM path); `DAEDAL_NO_FORWARD=1` disables forwarding and fails fast; if the VM is not Running the guard errors with `limactl start` instructions rather than forwarding. Portable scripts (`check-ascii.sh`, `fetch-guest-images.sh`, `patch-pvm-msr.py`) do not carry the guard.
- The x86_64 qemu VM requires `brew install lima-additional-guestagents`; without it `limactl start` fails with "guest agent binary could not be found for Linux-x86_64".
- Firecracker's child process opens `/dev/kvm`, so the daemon's user needs access. In production the systemd unit grants it via `SupplementaryGroups=kvm` (see `deploy/daedald.service`); the throwaway test scripts use `chmod 666 /dev/kvm`. `setfacl -m u:USER:rw /dev/kvm` is unreliable -- it grants the first firecracker but not the restore firecracker.
- Building firecracker requires `libseccomp-dev` (else the link fails with `cannot find -lseccomp`), even though a gnu-target build ships an empty runtime seccomp filter.

## PVM kernel
- The kernel source is `virt-pvm/linux` branch `pvm-612` (Linux 6.12.33). The `kernel/` tree in `dywongcloud/pvm-no-fsgsbase-rdtscp` is unusable -- it lacks all `arch/x86/**/*.S` assembly (0 `.S` files) and will not build.
- `kernel/patches/` holds five patches, all `git apply --check` clean on `pvm-612`: `0001-0004` are the no-FSGSBASE/RDTSCP series (decoded from the HTML-encoded source in the dywongcloud repo's `index.html`); `0005` is required for PVM snapshot restore (details in recall: FEAT_CTL host-initiated MSR fix).
- Host kernel config = the running Ubuntu config + `CONFIG_KVM_PVM=m`, keys cleared, BTF off, `LOCALVERSION=-pvm`, `UAPI_HEADER_TEST` off (PVM's `pvm_para.h` fails the standalone header test). The PVM kernel boots with `pti=off`.
- Guest kernel = same tree, canonical `virt-pvm/misc/pvm-guest-6.12.33.config` + `PVM_GUEST=y KVM_GUEST=y`, `make vmlinux` (uncompressed ELF firecracker boots directly). The guest rootfs must match the guest arch -- an x86_64 PVM guest needs an x86_64 busybox `/init` (an aarch64 one panics with `error -8`/ENOEXEC).
- The fallback series is inert when the CPU exposes FSGSBASE+RDTSCP (the fast path runs). To exercise it, boot with `clearcpuid=fsgsbase,rdtscp`; `dmesg` then shows "FSGSBASE not available... MSR-based" and "RDTSCP not available... trapped and emulated", and firecracker still boots a microVM via the fallback switcher.

## Firecracker migration
- The fork ships no migrate endpoint. Migration is orchestrated over `/snapshot/create` (Full+Diff), `/snapshot/load`, `/vm` pause/resume.
- Diff snapshots (`track_dirty_pages`) produce a sparse mem file; `internal/migrate/sparse.go` merges it onto the base with `SEEK_DATA`/`SEEK_HOLE`. The seek whence constants differ by OS (Linux `SEEK_DATA=3,SEEK_HOLE=4`; darwin `4,3`) -- `sparse.go` selects by `runtime.GOOS`. Real firecracker runs on Linux; the darwin path is local-dev only.
- Precopy's win is on *remote* migration (base memory streams while the guest runs; only the diff is downtime). For local migration precopy runs slightly slower than cold (two pauses, no transfer to overlap) -- expected, not a bug.
- PVM-under-qemu-TCG hits a transient firecracker exit after ~25 sustained back-to-back migrations (double-emulation artifact, no OOM/oops). The daemon's dead-instance detection marks the VM errored and rejects further migrations with 409. This does not occur on real virtualization (the KVM path is stable).

## Live migration (`api/internal/livemigrate`, `<= 30ms` blackout)
- The blackout is kept small by mapping guest memory lazily at the destination (a `File` backend mmaps the shared memfile; `Uffd` uses a userspace handler). No memory is copied during the cutover, so it is ~5ms. The one-time pre-copy Full snapshot pauses the source and scales with guest RAM (~14ms@32MiB, ~128ms@128MiB), so a small guest keeps every pause under 30ms.
- Firecracker opens the `/dev/userfaultfd` device node (not the syscall), so the Uffd backend needs `sysctl vm.unprivileged_userfaultfd=1` AND `chmod 666 /dev/userfaultfd`, alongside `chmod 666 /dev/kvm`.
- A read-only shared rootfs must be built with `mkfs.ext4 -O ^has_journal`; a journaled ext4 needs write access to replay its journal and panics read-only.
- The two "hosts" are podman `--rootfs` containers (image built by `scripts/build-host-image.sh` -- no registry pull; Lima's NAT stalls pulls) with `--network host`, a shared `/dev/shm`, and a bridge; the guest keeps its IP/MAC across hosts via Firecracker `network_overrides`. `--rootfs PATH` must come last, right before the command.
- `two-host-demo.sh` runs the image as an overlay (`--rootfs "$ROOTFS":O`) so podman never writes into the base image dir. Without `:O`, a `sudo podman run` injects root-owned files into the base (`/run/.containerenv`, the `-v` bind-mount point dirs), and the next unprivileged `rm -rf` in `build-host-image.sh` fails with "Permission denied". The overlay keeps the base pristine and user-owned; `build-host-image.sh` also `sudo rm -rf`s (guarded against `/`/`$HOME`) and stops stale `host-a`/`host-b` first, so both scripts are safely re-runnable. `$SHARED` (`/dev/shm/dhost`) collects root-owned files from `sudo daedald`/`sudo podman`, so the demo `sudo rm -rf`s it too.
- Cutover blackout over 100 single-host migrations (32 MiB, host idle): continued 100/100, p50 5.8 / p95 8.0 / p99 10.0 / max 11.2 ms, zero over 30 ms. Under competing host load (e.g. a browser on the macOS host during the run) nested virt can deschedule the whole VM and inflate one migration -- every cutover phase together -- to 30-50 ms (not the mechanism; bare-metal KVM does not), so run the benchmark host-idle. `scripts/blackout-p99.sh` gates on p95 (robust) and prints p99/max/over-target; run with `n >= 100` (at n=20 the reported "p99" is just the sample max). Continuity parses the guest heartbeat anchored on the console CRLF so firecracker's own stdout API logs cannot corrupt it (a whole-VM stall that interleaves a log line into a HEARTBEAT would otherwise misparse as a huge counter and false-fail a good migration).

## GUI desktop guests (React Flow visualization)
- DECISION (supersedes the old "desktop guests are never migrated" design): the XFCE desktop guest on the `host-a` card IS the VM that live-migrates. `daedald livemigrate serve -persistent-guest` boots ONE 1024MiB desktop guest at startup and every `POST /v1/migrations` live-migrates that same already-running guest between `host-a` and `host-b`, alternating direction, never rebooting or destroying it. The Migrate button therefore moves the real desktop, not a separate beacon guest. `livemigrate.Session` (`api/internal/livemigrate/session.go`) owns this; it reuses the same `precopy`/`cutover` helpers as `livemigrate.Run`, so there is exactly one migration implementation.
- CORRECTED (the old pinned-card design below was the direct cause of a real bug): a desktop card is a VIEW OF WHICHEVER HOST CURRENTLY HOLDS THE GUEST, never a card pinned to a guest identity for the life of the page. `web/src/App.tsx` holds `ownerHost` state seeded from `GET /v1/migrations/guest`'s `host` field and moved by `useMigrationEvents`'s `onOwnerChanged`, which fires only on `migration_complete` with the server's real destination; the desktop card under the owner gets the guest's `vncNodeId` and the other card is cleared to an empty id, which makes `useVncScreen` disconnect its RFB and drop to `idle`. The VNC edge is derived from `ownerHost` too, so only the owner host ever shows a `VNC 5901` edge. WITNESSED FAILURE of the superseded design: the persistent guest had been living on `host-b` for 15+ minutes (`GET /v1/migrations/guest` -> `host-b`, only `tap-lm-b` `LOWER_UP`, the single Firecracker on `host-b.sock`) while the GUI still drew the desktop on the `host-a` card, because the old code bound `host-a -> desktop-a` once at mount and never moved it. The stream identity is guest-scoped, not host-scoped: ONE `vnc-tunnel-agent` dials the guest IP that follows it across hosts, so there is exactly one NodeId to render and the only question is WHICH card renders it.
- Because the stream is guest-scoped, the per-host `POST /v1/hosts/{id}/vnc-endpoint` registry is at best a fallback and can be actively wrong: it is in-memory, register-only, with no expiry or liveness check, so a dead agent's EndpointId is served forever (witnessed: `GET /v1/hosts` returning two node ids for agents dialing `172.20.0.4:5901`, a guest that no longer exists). The GUI therefore resolves the guest node id `?vnc=` > `?nodeA=` (legacy alias) > the registry entry for the owner host.
- MEASURED on the 1024MiB desktop guest (real runs inside `daedal-kvm`, nested virt, three consecutive migrations of one running guest): cutover blackout **34.4 ms** on the first migration after boot (`load_resume` alone 27.9 ms), then **12.5 ms** and **10.6 ms** on the second and third. The one-time pre-copy Full snapshot pauses the guest for **1928 / 915 / 357 ms** respectively (it writes a 1 GiB memfile to the shared `/dev/shm` tmpfs while the guest is paused); whole-request wall time was 2973 / 1941 / 1419 ms. The `<= 30 ms` blackout figure in README.md is the 32 MiB beacon guest's and MUST NOT be widened to this guest: the first desktop migration measured above it. Steady-state desktop cutover is ~10-13 ms.
- Repeat migrations require dirty-page tracking on the RESTORED VM, so `Session` passes `enable_diff_snapshots: true` on `PUT /snapshot/load` (deprecated but present in Firecracker v1.17.0-dev). Without it migration #2's Diff snapshot would fail. `GET /v1/migrations/guest` reports the live guest's real `machine-config` so this is checkable (`track_dirty_pages: true` after a restore).
- The guest keeps MAC `06:00:AC:14:00:03` and IP `172.20.0.3` across hosts via Firecracker `network_overrides`, and both host taps sit on the same `br0`. WITNESSED: the bridge relearns the MAC on the destination tap by itself, `ping` is 0% loss and TCP 5901 still answers `RFB 003.008` after three migrations -- so ONE `vnc-tunnel-agent` dialling `172.20.0.3:5901` keeps working throughout and the VNC stream is not re-pointed on migration.
- Two Firecracker VMM processes, one per host name, each with its own tap and its own API socket under `-session-work-dir`; they run as plain processes in `daedal-kvm`, not podman containers (container-level host isolation is what `two-host-demo.sh` demonstrates for the beacon guest). Only one holds the guest at a time: the drained source VMM is killed after the destination resumes.
- HAZARD, hit for real: the desktop rootfs is mounted READ-WRITE, so two Firecracker processes opening the same image corrupt it. This happened when `daedald` booted the guest before binding its listen port, then died on `address already in use` and orphaned the VMM; `e2fsck -fy` then reported real inode-bitmap damage. Two fixes are in place -- `daedald` now binds the port BEFORE starting the session, and `StartSession` refuses to boot if a Firecracker is already live on either host's API socket. Note `pkill -x firecracker` does NOT find these processes: the binary is `firecracker-aarch64`, so `/proc/pid/comm` truncates to `firecracker-aar`. The demo script scans `/proc/*/comm` for `firecracker*` and matches the session work dir instead.
- Tap names are namespaced (`tap-lm-a`, `tap-lm-b`, `tap-lm-pin`). A generically-named tap is a shared resource: a `tap-desk-b` created by one session was deleted by another session's tap churn, wedging the running guest with `Failed to write to tap: Os { code: 77 ... File descriptor in bad state }` forever.
- In-guest witness channel: do NOT rely on the guest's sshd. It completes KEX and publickey auth but its session channel never answers the exec request (pam_systemd/logind hang in this image), so every remote command returns empty. Instead the session's Firecracker processes get a serial-console input fifo per host (`Session.console(i)`, reported as `console` by `GET /v1/migrations/guest`): write a line into that fifo to drive a root shell on `ttyS0` (root password `daedal`), and read the output back from the same host's serial log. This works on whichever host currently holds the guest, with no guest networking involved.
- DECISION: the desktop guest rootfs is a real Debian install via `debootstrap` (run inside `daedal-kvm`, which has apt and network access as Linux) -- not the 48MB busybox images used for the beacon/heartbeat guests. Confirmed present in Debian trixie (current stable, checked via the archive madison API): `tigervnc-standalone-server` (Xvnc = X server + VNC server in one process, replaces separate Xvfb+x11vnc), `xfce4`, `xfce4-terminal`, `dbus-x11`, `ifupdown`, `e2fsprogs`, `debootstrap` itself. debootstrap's default (non-`--variant=minbase`) install pulls in `systemd-sysv` (Priority: important in the Debian archive), so systemd is PID 1 with no extra steps. A dedicated `vncuser` runs `vncdesktop.service` (`su - vncuser -c 'vncserver :1 -geometry 1280x800 -SecurityTypes None -localhost no'`), enabled by default; `~/.vnc/xstartup` execs `startxfce4`. VNC is fixed at display `:1` -> TCP 5901. Guest networking is a static `/etc/network/interfaces` (ifupdown), matching the `network_overrides` static-IP convention already used for the beacon guest, parameterized by `GUEST_IP`/`GATEWAY_IP`/`NETMASK` (default `172.20.0.3`/`172.20.0.1`/`255.255.255.0`, distinct from the beacon guest's `172.20.0.2` on the same bridge). `scripts/build-desktop-rootfs.sh` implements this; `IMG_NAME` parameterizes the output filename so a second invocation (e.g. `GUEST_IP=172.20.0.4 IMG_NAME=rootfs-desktop-b`) builds the second host's distinct image instead of overwriting the first.
- `scripts/boot-desktop.sh` boots ONE standalone desktop guest directly against Firecracker's REST API over its unix socket (`PUT /boot-source`, `/drives/rootfs`, `/machine-config`, `/network-interfaces/eth0`, `/actions {InstanceStart}`) on a plain host bridge+tap, no podman container involved -- the guest is not migrated, so it does not need the podman `--rootfs :O` overlay trick two-host-demo.sh uses to keep the base image pristine across runs. Its rootfs path is currently a hardcoded constant (`rootfs-desktop.ext4`), so as-is it only covers one of the two desktop hosts; `scripts/desktop-migration-demo.sh` boots both by generalizing the same curl-to-unix-socket sequence with a distinct tap/MAC/rootfs image per host rather than invoking `boot-desktop.sh` twice against the same disk image (that would double-mount one read-write ext4 image from two Firecracker processes and collide both guests onto the same baked-in static IP).

## GUI Tier-1 design (React Flow + noVNC + iroh VNC tunnel + SSE)
- Browser: `web/` (Vite+React+`@xyflow/react`) renders one `MicroVMNode` per host and one `MigrationEdge` between them. On mount it `GET`s `http://localhost:7040/v1/hosts` to learn each host's real iroh `EndpointId` and subscribes to `GET http://localhost:7040/v1/migrations/events` (SSE) to flip `migrationHighlight`/`migrating`/`fadingOut` off the DESKTOP guest migration's real `migration_start`/`migration_progress`/`migration_complete`/`migration_failed` events -- the edge animation and the desktop card's relocation are both keyed to that real SSE stream, not a timer. `MigrateButton` `POST`s `http://localhost:7040/v1/migrations` with an EMPTY body `{}`: in `-persistent-guest` mode the handler ignores `mem_mib`/`from`/`to` entirely and derives the direction from `session.CurrentHost()`/`NextHost()`, so a body claiming `{mem_mib: 32, from, to}` (what it used to send) was pure decoration that also lied about a 1024MiB guest. The button's own state is now props from `App.tsx` (`currentHost`, `nextHost`, `inFlight`) rather than a second EventSource and a second `/v1/migrations/current-host` fetch -- two subscribers to one SSE stream could disagree about who owns the guest.
- Per-host VNC path: `vnc-tunnel-agent` (`gateway/`, Rust) runs next to each desktop guest, binds an iroh `Endpoint` on ALPN `daedal-vnc/1`, and prints its `EndpointId` -- the value registered with daedald via `POST /v1/hosts/{id}/vnc-endpoint`. `vnc-ws-gateway` runs once on the macOS host, bridges browser WebSocket connections (`ws://.../vnc?node=<EndpointId>`) to an iroh dial at that node, and both binaries hand raw bytes to `gateway_relay_common::relay` (`tokio::io::copy` both directions) since RFB is already self-framed -- no envelope needed end to end.
- STALE, now false: this line used to say the desktop guests are never the migration subject and only a separate beacon guest is. The persistent-guest mode above makes the 1024MiB XFCE desktop guest the migration subject itself, and the GUI's desktop card follows it.
- `scripts/desktop-migration-demo.sh` wires all of the above for a live demo: rebuilds `daedald` (cross-compiled `GOOS=linux GOARCH=arm64 CGO_ENABLED=0`, no C toolchain needed, run directly on macOS -- confirmed this needs no VM), starts `daedald livemigrate serve` and a `two-host-demo.sh`-style beacon container pair inside `daedal-kvm`, boots both desktop guests, starts both `vnc-tunnel-agent`s and registers their real NodeIds, starts `vnc-ws-gateway` on macOS, builds and serves `web/dist`, and prints the demo URL. It is a mixed macOS/VM driver (not a single `require_linux`-forwarded script like its siblings): `daedald` and `vnc-ws-gateway` run on macOS directly; the Firecracker guests, `vnc-tunnel-agent`, and `daedald livemigrate serve` run inside `daedal-kvm` via explicit `limactl shell` (they need `/dev/kvm` or the guest's bridge IP). This works because Lima's `vz` driver auto-forwards a guest process's `127.0.0.1:PORT` listener to the same `127.0.0.1:PORT` on the macOS host with no `portForwards` config needed -- confirmed live (`python3 -m http.server` inside `daedal-kvm` was immediately reachable via plain `curl http://127.0.0.1:<port>/` from macOS) -- which is exactly why `daedald` can run inside the VM yet still answer the frontend's hardcoded `http://localhost:7040`.

## GUI Tier-2 video (iroh-live H.264/MoQ) -- BUILT AND PROVEN, real H.264 frames decode in a real browser

Tier-1 (VNC-over-iroh, `gateway/vnc-tunnel-agent` + `gateway/vnc-ws-gateway`) is untouched and still the default; Tier-2 is a fully separate, additional path.

Run plain (`./target/release/iroh-live-relay`, no `--dev` flag in this pinned version -- self-signed TLS is unconditional); prints `iroh-live relay listening at http://localhost:4443` (the static web viewer, plain HTTP -- **not** the same thing as the `https://localhost:4443` line right below it, which names the separate QUIC/WebTransport+TLS listener sharing the same port number over a different transport). - **Known real bug in the vendored `@moq/lite` build, patched locally**: `node_modules/@moq/lite/connection/connect.js`'s `Promise.any([websocket, webtransport])` never settles if the WebSocket fallback branch hangs (never resolves *or* rejects) -- which it does against this relay's axum router, since `iroh-live-relay`'s `static_router` (`iroh-live-relay/src/lib.rs`) only defines plain GET routes and has no WebSocket-upgrade handler at all. `Promise.any` needs every branch to reach a terminal state before it can reject, so one perpetually-pending branch blocks the whole connection forever even though WebTransport alone works. Fix applied: hardcode `const websocket = false ? ... : undefined;` in that file (disables the fallback), then `cd holoiroh-vendor/iroh-live-patched/iroh-live-relay/web && npm run build` (regenerates `dist/`) then `cargo build --release -p iroh-live-relay` (re-embeds `dist/` via `include_dir!`) to pick it up. This edit lives in `node_modules/` (gitignored, not committed) -- re-apply it after any `npm install` in that directory.

## Verification
- No unit-test files. Every check is a live `exec_js`/`curl` against a running daemon (mock backend for CI, real firecracker in the VM). `bench/ci-verify.sh` is the CI gate; `daedald bench` asserts p99 < 20s and exits non-zero otherwise.
